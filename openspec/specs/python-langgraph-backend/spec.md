# Python LangGraph Backend Spec

## Technology

- The Python backend MUST live under `python-backend/`.
- The Python backend MUST declare Python `>=3.11`.
- The Python backend MUST use FastAPI for HTTP APIs.
- The Python backend MUST use LangGraph for conversation orchestration.
- The Python backend MUST use async I/O for database and streaming work.

## API Compatibility

- The Python backend MUST expose the same frontend-facing API paths as the Java backend.
- The Python backend MUST return response fields using the same frontend-facing names, such as `createdAt`, `updatedAt`, `modelName`, `skillId`, and `attachmentIds`.
- The Python backend MUST stream the same `started`, `reasoning`, `delta`, `completed`, and `failed` event types.

## LangGraph Flow

- The chat flow MUST include a graph step that composes prompt messages.
- The chat flow MUST include a graph step that summarizes or records loaded context.
- The graph output MUST be used before invoking the model gateway.
- Reasoning generated by the graph SHOULD be streamed as `reasoning` events before answer deltas.
- The graph state SHOULD include RAG contexts and MCP tool descriptors when enabled.

## RAG And MCP

- The Python backend MUST expose `GET /api/rag/search`.
- The Python backend MUST expose `GET /api/mcp/tools`.
- The Python backend MUST expose `POST /api/mcp/tools/{toolName}/invoke`.
- RAG MUST be provided through a service boundary so configured local documents can later be replaced by vector retrieval.
- MCP MUST be provided through a service boundary so future tools and remote MCP servers can be added without changing FastAPI routes.
- The `context.search` MCP tool MUST call the RAG retrieval service.
- Response field names SHOULD remain frontend-compatible with the Java backend, including `sourceId` and `toolName`.

## Model Gateway

- The Python backend MUST provide a local fallback model.
- The Python backend MUST provide an OpenAI-compatible streaming gateway.
- If a configured model has no API key, the backend SHOULD route to the local fallback behavior rather than crashing during development.
- Remote model errors MUST be converted into user-readable failed events.

## Persistence

- The Python backend MUST connect to openGauss using PostgreSQL-compatible asyncpg.
- The Python backend MUST ensure schema idempotently at startup.
- The asyncpg pool MUST use an openGauss-compatible reset strategy.
- Conversation, message, attachment, and dynamic Skill storage MUST match the Java backend schema.

## Tests

- The Python backend MUST include unit tests for LangGraph prompt composition.
- The Python backend MUST include unit tests for local fallback streaming.
- The Python backend MUST include unit tests for Markdown and Excel export behavior.
- Tests MUST pass with the repository-managed virtual environment once dependencies are installed.
